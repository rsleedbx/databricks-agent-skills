# Prerequisite checks

Checks to run and confirmations to get before any Lakeflow Connect pipeline is created. The short list is in [SKILL.md](../SKILL.md#prerequisites).

**Destination tables: LFC names them, the user places them.** A destination table takes its source table's name; every object needs its `destination_catalog` and `destination_schema`, and a schema object brings every table of the source schema (and later ones) under their own names. Nothing renames a clash: two source tables with the same name (`sales.orders`, `finance.orders`) need a destination schema each or a `destination_table`, and the pipeline create doesn't catch a clash (the first update fails). Check the mapping before deploying; see [integrated-cdc.md](integrated-cdc.md#where-each-table-lands-what-lfc-names-what-you-choose).

**Ask before creating anything.** If the user hasn't named a source, ask which database or app to ingest from. For Postgres, offer two choices: an existing database (host, port, database, read-only user), or a Lakebase demo stand-in, which runs end to end with [lakebase-as-postgres-source.md](lakebase-as-postgres-source.md) (its Step 0 lists the inputs to collect). If the user names an existing UC connection but not the tables, list them first with Step 0 of [query-based-discovery.md](query-based-discovery.md), and propose tables from what you find. For full detail, introspect the whole database in one shot with [source-sql-through-connection.md](source-sql-through-connection.md) (all columns in one query, all keys and indexes in another, never table by table). If the connection sees more than one database, ask which one. Never stand up a stand-in source (a Lakebase project or branch, a new database, seed tables) on your own. Before a query-based pipeline, run the pre-flight checks in [query-based-connectors.md](query-based-connectors.md#pre-flight-checks-before-creating-the-pipeline-advise-the-product-doesnt-check): the product doesn't verify that a declared key is unique, that the cursor is indexed, or that it has no NULLs. Report what you find, and let the user skip it (for example for a snapshot or a test). Ask for every missing input in one message, list what you'll create (source, UC connection, target schema, pipeline, job), and wait for one "yes". Then run the whole setup without asking again.

Confirm before creating any pipeline:

1. **A Unity Catalog target** — catalog and schema must exist. **CDC pipelines (integrated and standard) can't use a Default Storage catalog**: create fails with "Default Storage for Unity Catalog is not supported on LakeFlow Connect pipelines". Query-based pipelines work there. A catalog is on Default Storage when its `storage_root` is under the URL of the system external location `__databricks_managed_storage_location` (`databricks external-locations get __databricks_managed_storage_location`). Check before building CDC, and if it is, ask for a catalog with its own managed location. A catalog with its own location can still fail at create with "Azure storage credential was not found. The access connector may have been deleted or recreated": its storage credential is broken, so use another catalog and tell the user. On a metastore with no storage root, `databricks catalogs create` fails, while SQL `CREATE CATALOG <name>` creates a Default Storage catalog: fine for query-based, not for CDC. Beyond that, the service principal or user creating the pipeline needs `USE CATALOG`, `USE SCHEMA`, `CREATE TABLE`, and `MODIFY` on the target schema.
2. **A UC `CONNECTION` object** with credentials for the source. SaaS OAuth U2M connections must be created via the UI (Catalog Explorer); API-key, basic-auth, and database connections can be created via CLI / DAB. Creating one requires `CREATE CONNECTION` on the metastore.
3. **For CDC database connectors**: network reachability from the compute that reads the change log to the source database. That's the integrated CDC pipeline itself, or the gateway for standard CDC. Serverless or classic depends on the current docs and the workspace's compute policy. On-prem requires ExpressRoute (Azure) or Direct Connect (AWS).
4. **For query-based connectors**: network reachability from **serverless** compute to the source, plus a monotonic cursor column (e.g. `updated_at`, bumped on every update) on each table.
5. **For file connectors**: OAuth scope grants on the SaaS file repo (SharePoint / Google Drive).
